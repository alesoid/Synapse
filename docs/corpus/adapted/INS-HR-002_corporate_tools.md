## 1. Назначение

Настоящий документ устанавливает обязательные правила использования корпоративных инструментов Synapse Corp: систем коммуникации, управления задачами, контроля версий и инфраструктуры. Соблюдение правил обеспечивает безопасность данных, прозрачность работы и предсказуемость процессов.

## 2. Корпоративный стек инструментов

| Категория | Инструмент | Назначение |
|---|---|---|
| Коммуникация | Slack | Основной канал рабочего общения |
| Видеосвязь | Zoom | Встречи, 1:1, демо |
| Управление задачами | Jira | Спринты, тикеты, трекинг времени |
| Контроль версий | GitLab | Репозитории, MR, CI/CD |

Использование личных аккаунтов сторонних сервисов для рабочих задач **не допускается**.

## 3. Slack — правила работы

### 3.1 Общие принципы

- Slack — единственный канал оперативной рабочей коммуникации. Личные мессенджеры (Telegram, WhatsApp) для рабочих вопросов не используются.
- Рабочий профиль заполняется полностью: имя, фамилия, должность, часовой пояс, аватар.
- Статус обновляется при отсутствии на рабочем месте (встреча, обед, недоступен).

### 3.2 Каналы

| Тип канала | Назначение | Пример |
|---|---|---|
| `#general` | Общие объявления | Релизы, новости компании |
| `#team-<название>` | Рабочие вопросы команды | `#team-backend` |
| `#project-<название>` | Обсуждение конкретного проекта | `#project-synapse` |
| `#incidents` | Инциденты и сбои | Только по назначению |
| `#random` | Неформальное общение | |

- Рабочие вопросы обсуждаются в тематических каналах, не в личных сообщениях.
- Личные сообщения используются только для приватных вопросов, не касающихся команды.
- Теги `@channel` и `@here` используются только при критических уведомлениях.

### 3.3 Асинхронная культура

- Ответ на сообщение ожидается в течение рабочего дня — немедленный ответ не обязателен.
- Для срочных вопросов явно указывается приоритет: `[СРОЧНО]` в начале сообщения.
- Нерабочее время (после 19:00 и выходные) — уведомления отключать, ответ не ожидается.

## 4. Jira — правила работы

### 4.1 Работа с тикетами

- Каждая задача фиксируется в Jira до начала работы — работа без тикета не допускается.
- Статус тикета обновляется в день изменения: `To Do → In Progress → In Review → Done`.
- Описание тикета содержит: цель задачи, критерии приёмки, ссылки на связанные задачи.
- Затраченное время логируется в тикете в день выполнения работы.

### 4.2 Именование веток

Ветка в GitLab создаётся с привязкой к тикету Jira:

```
feature/SYN-123-краткое-описание
bugfix/SYN-456-описание-бага
hotfix/SYN-789-критический-фикс
```

### 4.3 Приоритеты

| Приоритет | Описание | Ожидаемая реакция |
|---|---|---|
| Critical | Продакшн сломан | Немедленно, в рабочее время |
| High | Блокирует команду | В течение текущего дня |
| Medium | Плановая задача | В рамках спринта |
| Low | Nice to have | По мере возможности |

## 5. GitLab — правила работы

### 5.1 Репозитории и доступ

- Доступ к репозиториям выдаётся IT-отделом по заявке через Jira.
- Принцип минимально необходимых прав: доступ только к репозиториям текущего проекта.
- Личные форки корпоративных репозиториев **запрещены**.
- Корпоративный код не переносится в личные аккаунты или сторонние сервисы.

### 5.2 Коммиты

Сообщение коммита содержит номер тикета и краткое описание изменения:

```
SYN-123: добавить эндпоинт /query с фильтрацией по ролям
SYN-456: исправить баг с кодированием UTF-8 в парсере PDF
```

- Прямые коммиты в ветки `main` и `develop` **запрещены**.
- Один коммит — одно логическое изменение. Коммиты типа «разные правки» не допускаются.

### 5.3 Merge Requests

- MR открывается с описанием изменений, ссылкой на тикет Jira и чеклистом проверки.
- MR без прохождения CI/CD пайплайна в ревью не принимается.
- Минимум один апрув от ревьюера обязателен перед слиянием.
- Правила код-ревью описаны в документе `STD-ENG-001`.

## 6. Управление паролями и доступами

- Все рабочие учётные данные хранятся исключительно в корпоративном менеджере паролей.
- Хранение паролей в браузере, текстовых файлах, мессенджерах **запрещено**.
- Пароли корпоративных аккаунтов не передаются коллегам — при необходимости доступ оформляется через IT.
- MFA активируется на всех корпоративных сервисах в обязательном порядке.
- VPN активируется при любом подключении к корпоративной инфраструктуре вне офиса.

---

## 7. Использование корпоративного оборудования

- Корпоративный ноутбук используется преимущественно в рабочих целях.
- Установка стороннего ПО согласовывается с IT-отделом.
- Корпоративные данные не хранятся на личных устройствах без согласования с IT.
- При утере или краже оборудования незамедлительно уведомляется IT-отдел и непосредственный руководитель.

---

## 8. Конфиденциальность и безопасность

- Корпоративные данные, код, архитектурные решения и переписка не передаются третьим лицам.
- Скриншоты внутренних систем не публикуются в открытых источниках.
- Подозрительная активность (фишинг, несанкционированный доступ) немедленно сообщается в `#incidents`.
- Политика информационной безопасности описана в документе `POL-SEC-001`.
