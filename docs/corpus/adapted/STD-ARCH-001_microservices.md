## 1. Назначение

Настоящий стандарт определяет архитектурные принципы, требования к проектированию и ограничения для микросервисов Synapse Corp. Соблюдение стандарта обеспечивает согласованность архитектуры, управляемость технического долга и готовность системы к масштабированию.

---

## 2. Принципы архитектуры

| Принцип | Описание |
|---|---|
| **Single Responsibility** | Каждый сервис решает одну бизнес-задачу |
| **Loose Coupling** | Сервисы взаимодействуют через явные контракты (API), не через общую БД |
| **High Cohesion** | Связанная функциональность находится в одном сервисе |
| **Design for Failure** | Каждый сервис рассчитывает на недоступность зависимостей |
| **Security by Design** | Проверка прав доступа — обязанность каждого сервиса, а не шлюза |

---

## 3. Структура сервиса

### 3.1 Обязательные компоненты

Каждый микросервис Synapse Corp содержит:

```
service-name/
├── api/            # Эндпоинты, модели запросов/ответов
├── core/           # Бизнес-логика
├── db/             # Клиенты баз данных, репозитории
├── models/         # Доменные модели
├── security/       # Проверка прав доступа
├── tests/          # Unit и интеграционные тесты
├── Dockerfile
├── requirements.txt
└── README.md       # Обязателен (см. STD-ENG-003)
```

### 3.2 Конфигурация

- Вся конфигурация передаётся через переменные окружения
- Значения по умолчанию задаются только для dev-окружения
- Секреты не хранятся в коде и не коммитятся в репозиторий
- Переменные документируются в README и `.env.example`

## 4. API-контракты

### 4.1 REST API

- Именование ресурсов — существительные во множественном числе: `/documents`, `/chunks`
- HTTP-методы используются по назначению: GET (чтение), POST (создание), PUT/PATCH (обновление), DELETE (удаление)
- Версионирование API: `/api/v1/...`
- Ответы содержат HTTP-статус коды согласно RFC 7231

### 4.2 Формат ошибок

```json
{
  "error": {
    "code": "ACCESS_DENIED",
    "message": "Недостаточно прав для доступа к документу",
    "request_id": "uuid"
  }
}
```

### 4.3 Документация API

- Все эндпоинты документируются через OpenAPI / Swagger
- Swagger UI доступен по `/docs` в dev-окружении
- Изменение публичного API без обновления спецификации не допускается

## 5. Взаимодействие между сервисами

### 5.1 Синхронное взаимодействие (REST/HTTP)

Используется для:
- Запросов, требующих немедленного ответа
- Операций с пользовательскими данными в реальном времени

Требования:
- Таймауты настроены явно (не более 30 секунд)
- Реализован retry с экспоненциальной задержкой
- Circuit breaker при систематических сбоях зависимости

### 5.2 Асинхронное взаимодействие

Используется для:
- Длительных операций (ingestion документов, перестроение графа)
- Событий, не требующих немедленного ответа

---

## 6. Управление данными

- Каждый сервис владеет своими данными — прямой доступ к БД другого сервиса **запрещён**
- Общие данные передаются через API
- Схема БД версионируется через миграции
- Резервное копирование — ответственность DevOps, настраивается при выводе в продакшн

---

## 7. Безопасность

- Все входящие запросы проходят проверку роли пользователя (`X-User-Role` заголовок)
- Фильтрация данных по `access_level` выполняется на уровне запроса к БД, а не постфактум
- PII-данные в логах не пишутся
- Детальная политика доступа описана в `POL-SEC-001`

---

## 8. Observability

Каждый сервис в продакшн-окружении обеспечивает:

| Компонент | Требование |
|---|---|
| Healthcheck | Эндпоинт `GET /health` с проверкой зависимостей |
| Метрики | Prometheus: latency, RPS, error rate |
| Трейсинг | OpenTelemetry: span для каждой операции с внешними зависимостями |
| Логирование | Структурированные логи (JSON), уровни: DEBUG / INFO / WARNING / ERROR |

---

## 9. Технический долг

- Технический долг фиксируется в Jira с тегом `tech-debt` в день обнаружения
- Критический технический долг (влияет на безопасность или стабильность) эскалируется Tech Lead немедленно
- Плановое погашение технического долга — до 20% ёмкости каждого спринта
- Политика управления техническим долгом описана в `POL-ARCH-001`
