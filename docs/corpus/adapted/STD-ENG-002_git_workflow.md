## 1. Назначение

Настоящее руководство устанавливает обязательную модель ветвления, правила именования и порядок работы с Git-репозиториями Synapse Corp. Соблюдение стандарта обеспечивает чистоту истории изменений, предсказуемость релизного процесса и минимизацию конфликтов слияния.

---

## 2. Модель ветвления

Synapse Corp использует модель **GitFlow** с адаптациями под CI/CD.

### 2.1 Постоянные ветки

| Ветка | Назначение | Прямые коммиты |
|---|---|---|
| `main` | Стабильная версия, готовая к продакшну | Запрещены |
| `develop` | Интеграционная ветка, основа для разработки | Запрещены |

Обе ветки защищены: слияние только через MR с апрувом.

### 2.2 Временные ветки

| Тип | Префикс | Создаётся из | Сливается в |
|---|---|---|---|
| Новая функциональность | `feature/` | `develop` | `develop` |
| Исправление бага | `bugfix/` | `develop` | `develop` |
| Подготовка релиза | `release/` | `develop` | `main` + `develop` |
| Критическое исправление | `hotfix/` | `main` | `main` + `develop` |

---

## 3. Именование веток

Формат: `<тип>/SYN-<номер>-<краткое-описание>`

```
feature/SYN-123-graphrag-hybrid-search
bugfix/SYN-456-fix-rbac-filter-neo4j
hotfix/SYN-789-critical-token-leak
release/v1.2.0
```

Правила:
- Только строчные буквы, цифры и дефисы
- Номер тикета Jira обязателен для feature и bugfix
- Описание — кратко, по-русски или по-английски, не длиннее 5 слов

---

## 4. Правила коммитов

### 4.1 Формат сообщения коммита

```
SYN-123: краткое описание изменения (до 72 символов)

Опциональное расширенное описание — что и почему изменено.
Не как изменено (это видно из diff).
```

Примеры:
```
SYN-234: добавить фильтрацию чанков по access_level в Qdrant
SYN-345: исправить кодировку UTF-8 при парсинге PDF
SYN-456: рефакторинг entity_extractor — вынести промпт в константы
```

### 4.2 Требования к коммитам

- Один коммит — одно логическое изменение
- Коммиты типа «правки», «wip», «fix» без контекста не допускаются
- Секреты, пароли, токены в коммитах **категорически запрещены**
- История коммитов в MR должна быть читаемой — squash при необходимости

## 5. Процесс разработки

### 5.1 Стандартный цикл (feature)

```
1. Создать ветку из актуального develop
   git checkout develop && git pull
   git checkout -b feature/SYN-123-описание

2. Разработка и коммиты
   git commit -m "SYN-123: ..."

3. Перед открытием MR — синхронизация с develop
   git fetch origin
   git rebase origin/develop

4. Открыть MR в GitLab
   - Заполнить описание по шаблону (см. STD-ENG-001)
   - Убедиться что CI/CD пайплайн зелёный

5. После апрува — слияние через GitLab UI
6. Удалить ветку после слияния
```

### 5.2 Hotfix

```
1. Создать ветку из main
   git checkout main && git pull
   git checkout -b hotfix/SYN-789-описание

2. Исправление, тест, коммит
3. MR одновременно в main и develop
4. После слияния — тег релиза на main
```

### 5.3 Release

```
1. Создать ветку из develop
   git checkout -b release/v1.2.0

2. Финальное тестирование, только bugfix коммиты
3. MR в main — тег версии
4. MR в develop — перенести исправления
```

---

## 6. Merge vs Rebase

| Операция | Когда использовать |
|---|---|
| `rebase` | Обновление feature-ветки до актуального develop перед MR |
| `merge` | Слияние через GitLab MR (сохраняет историю) |
| `squash merge` | При необходимости сжать историю MR в один чистый коммит |

`git push --force` в общие ветки (`main`, `develop`) **запрещён**.

---

## 7. Теги и версионирование

Synapse Corp использует **Semantic Versioning**: `vMAJOR.MINOR.PATCH`

| Изменение | Версия |
|---|---|
| Несовместимые изменения API | MAJOR |
| Новая функциональность, обратная совместимость | MINOR |
| Исправление багов | PATCH |

Теги создаются только на ветке `main` после слияния release или hotfix.
