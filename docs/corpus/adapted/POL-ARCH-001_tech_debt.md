## 1. Назначение

Настоящая политика определяет порядок выявления, классификации, фиксации и планового погашения технического долга в Synapse Corp. Неуправляемый технический долг снижает скорость разработки, увеличивает риски инцидентов и демотивирует команду. Управляемый — является нормальной частью процесса.

**Технический долг** — это намеренный или ненамеренный выбор более быстрого, но менее качественного решения, последствия которого потребуют дополнительных усилий в будущем.

---

## 2. Классификация технического долга

| Класс | Описание | Примеры |
|---|---|---|
| **Критический** | Влияет на безопасность или стабильность продакшна | Уязвимость, утечка данных, нестабильная зависимость |
| **Архитектурный** | Структурные решения, затрудняющие масштабирование | Монолитный модуль там, где нужен сервис; циклические зависимости |
| **Кодовый** | Проблемы качества кода | Дублирование логики, отсутствие тестов, «спагетти-код» |
| **Инфраструктурный** | Устаревшие зависимости, конфигурации | Непинированные версии образов, устаревшие библиотеки |
| **Документационный** | Отсутствующая или устаревшая документация | README не обновлён, ADR не написан |

---

## 3. Процесс работы с техническим долгом

### 3.1 Фиксация

- Любой сотрудник фиксирует обнаруженный технический долг в Jira с тегом `tech-debt`
- Тикет содержит: описание проблемы, класс долга, оценочное влияние, предлагаемое решение
- Замалчивание технического долга недопустимо — это усугубляет проблему

### 3.2 Приоритизация

Tech Lead проводит ревью `tech-debt` тикетов раз в две недели:

| Класс | Срок рассмотрения | Целевой срок погашения |
|---|---|---|
| Критический | Немедленно после обнаружения | Текущий спринт |
| Архитектурный | В течение недели | Следующие 1–2 спринта |
| Кодовый | В рамках планового ревью | В течение квартала |
| Инфраструктурный | В рамках планового ревью | В течение квартала |
| Документационный | В рамках планового ревью | До следующего релиза |

### 3.3 Погашение

- До **20% ёмкости каждого спринта** резервируется для погашения технического долга
- Погашение технического долга не откладывается бессрочно ради новых фич
- Решение о превышении 20% порога принимает Engineering Manager совместно с CTO

---

## 4. Принятие осознанного технического долга

Иногда технический долг принимается намеренно — для ускорения доставки. Это допустимо при соблюдении условий:

- Решение явно зафиксировано как технический долг в Jira в момент принятия
- Указан срок погашения (не позднее следующего квартала)
- Tech Lead уведомлён и согласен с решением
- Принятый долг не относится к классу «Критический»

Технический долг, принятый без фиксации, считается нарушением настоящей политики.

---

## 5. Метрики

Tech Lead отслеживает ежеквартально:

| Метрика | Целевое значение |
|---|---|
| Объём открытых `tech-debt` тикетов | Снижение или стабилизация |
| Доля спринта на погашение долга | 15–20% |
| Критических долгов старше 2 недель | 0 |
| Архитектурных долгов старше квартала | < 3 |

---

## 6. Ответственность

| Роль | Ответственность |
|---|---|
| Разработчик | Фиксировать долг при обнаружении |
| Tech Lead | Приоритизация, планирование погашения, ревью метрик |
| Engineering Manager | Выделение ёмкости спринта, эскалация при накоплении критического долга |
| CTO | Утверждение стратегических решений по архитектурному долгу |
