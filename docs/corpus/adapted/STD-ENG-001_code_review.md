## 1. Назначение

Настоящий стандарт устанавливает обязательные правила проведения код-ревью в Synapse Corp. Цель — обеспечить качество кода, распространение знаний внутри команды и предсказуемость процесса разработки.

Код-ревью — это профессиональная обратная связь по коду, а не оценка личности автора. Комментарии направлены на улучшение решения, а не на критику разработчика.

---

## 2. Область применения

Код-ревью обязательно для:
- любых изменений в ветках `main` и `develop`
- всех Merge Request (MR) независимо от объёма изменений
- изменений в конфигурации инфраструктуры и CI/CD пайплайнах

---

## 3. Роли и ответственность

| Роль | Ответственность |
|---|---|
| Автор MR | Подготовка кода, описание изменений, ответы на комментарии |
| Ревьюер | Проверка кода, конструктивные комментарии, апрув или запрос правок |
| Tech Lead | Финальный апрув для изменений в архитектуре или критических модулях |

---

## 4. Подготовка Merge Request

### 4.1 Обязательные условия перед открытием MR

- [ ] Все автоматические проверки пройдены: тесты, линтеры, CI/CD пайплайн
- [ ] Код соответствует принятым стайл-гайдам команды
- [ ] Ветка обновлена до актуального состояния `develop`
- [ ] Конфликты слияния разрешены автором
- [ ] Код самостоятельно проверен автором перед отправкой на ревью

### 4.2 Размер MR

- Оптимальный размер MR — до 400 строк изменений
- Крупные задачи разбиваются на последовательные MR, каждый из которых работоспособен независимо
- MR типа «разные правки» не допускается — один MR решает одну логическую задачу

### 4.3 Описание MR

Описание MR содержит обязательные разделы:

```
## Задача
Ссылка на тикет Jira: SYN-XXX
Краткое описание того, что и зачем изменяется.

## Что сделано
Краткое описание реализованного решения.

## Как проверить
Шаги для воспроизведения и проверки изменений.

## Чеклист
- [ ] Тесты написаны / обновлены
- [ ] Документация обновлена (если применимо)
- [ ] Нет hardcoded значений и секретов
```

---

## 5. Проведение ревью

### 5.1 Сроки

| Приоритет MR | Срок первого ревью |
|---|---|
| Critical / Hotfix | В течение 2 часов в рабочее время |
| High | До конца текущего рабочего дня |
| Normal | В течение 1 рабочего дня |

### 5.2 Что проверяет ревьюер

**Корректность:**
- Код решает поставленную задачу
- Граничные случаи и ошибки обработаны
- Нет очевидных багов и регрессий

**Качество:**
- Код читаем и понятен без дополнительных пояснений
- Нет дублирования логики
- Функции и методы имеют единственную ответственность
- Нет избыточной сложности

**Безопасность:**
- Нет hardcoded секретов, паролей, токенов
- Пользовательский ввод валидируется
- Права доступа проверяются там, где это необходимо

**Тесты:**
- Новая логика покрыта тестами
- Тесты проверяют поведение, а не реализацию

### 5.3 Классификация комментариев

Ревьюер явно указывает тип комментария:

| Тип | Значение | Пример |
|---|---|---|
| `[блокер]` | Обязательно исправить до апрува | Уязвимость безопасности, неверная логика |
| `[важно]` | Настоятельно рекомендуется исправить | Нарушение архитектурного принципа |
| `[нит]` | Незначительное замечание, на усмотрение автора | Стиль именования |
| `[вопрос]` | Запрос пояснения, не требует правок | Уточнение намерения автора |
| `[идея]` | Предложение для обсуждения | Альтернативный подход |

### 5.4 Правила для ревьюера

- Комментарии формулируются конкретно: указывается проблема и предлагается решение
- Не допускаются комментарии, направленные на личность автора
- Если замечаний нет — ревьюер явно одобряет MR с комментарием о проверке
- При несогласии с подходом ревьюер аргументирует позицию, а не просто отклоняет

---

## 6. Работа с комментариями (автор)

- Каждый комментарий обрабатывается явно: исправлен, отклонён с обоснованием или вынесен в отдельный тикет
- Исправления вносятся отдельными коммитами с пометкой `review: ...`
- При несогласии с комментарием автор аргументирует позицию — итоговое решение принимает Tech Lead
- После внесения правок автор уведомляет ревьюера

---

## 7. Апрув и слияние

- Для слияния MR требуется минимум **1 апрув** от ревьюера
- Для изменений архитектуры или публичного API — апрув Tech Lead обязателен
- Слияние выполняется автором после получения всех необходимых апрувов
- После слияния ветка удаляется
