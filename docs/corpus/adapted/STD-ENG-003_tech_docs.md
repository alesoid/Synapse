## 1. Назначение

Настоящий стандарт определяет требования к структуре, содержанию и оформлению технической документации Synapse Corp. Единый формат документации сокращает время на онбординг, упрощает ревью и снижает риск расхождений между документацией и реализацией.

Принцип: **документация — часть задачи, а не отдельный этап после сдачи**.

---

## 2. Типы документов и их назначение

| Тип | Когда создаётся | Хранится |
|---|---|---|
| README сервиса | При создании нового сервиса / репозитория | Корень репозитория |
| Спецификация микросервиса | При проектировании новой функциональности | Confluence / вики |
| API-документация | При добавлении или изменении API | Swagger / вики |
| Architecture Decision Record (ADR) | При принятии значимого архитектурного решения | `/docs/ADR/` |
| Runbook | При выводе сервиса в продакшн | Confluence / вики |
| Postmortem | После инцидента | Confluence / вики |

## 3. README сервиса

README — обязательный документ для каждого сервиса и репозитория. Содержит:

```markdown
# Название сервиса

Одна строка: что делает сервис.

## Назначение
Краткое описание: какую проблему решает, место в архитектуре.

## Быстрый старт
Минимальные шаги для запуска локально:
1. ...
2. ...

## Конфигурация
Переменные окружения и их назначение.

## API
Ключевые эндпоинты или ссылка на полную документацию.

## Зависимости
Другие сервисы и системы, от которых зависит данный сервис.

## Мониторинг
Ссылки на дашборды Grafana, алерты.

## Владелец
Команда или конкретный сотрудник, ответственный за сервис.
```

## 4. Спецификация микросервиса

Спецификация создаётся аналитиком или разработчиком до начала реализации. Обязательные разделы:

### 4.1 Общее описание
- Назначение сервиса
- Место в общей архитектуре (с указанием связей с другими сервисами)
- Ссылка на тикет Jira

### 4.2 Функциональные требования
Список требований в формате: `FR-XX: [описание]`

### 4.3 API
Для каждого эндпоинта:
- Метод и путь
- Входные параметры (типы, обязательность)
- Формат ответа
- Коды ошибок

### 4.4 Модель данных
- Схема сущностей
- Описание ключевых полей
- Связи с другими сущностями

### 4.5 Нефункциональные требования
- Ожидаемая latency
- Требования к масштабируемости
- Ограничения

## 5. Architecture Decision Record (ADR)

ADR фиксирует значимые архитектурные решения и обоснование выбора. Создаётся при выборе технологии, изменении архитектурного подхода или отклонении от существующих стандартов.

Шаблон ADR:

```markdown
# ADR-XXX: Краткий заголовок решения

**Дата:** ДД.ММ.ГГГГ
**Статус:** Предложено / Принято / Отклонено / Устарело
**Автор:** Имя

## Контекст
Описание проблемы или ситуации, требующей решения.

## Решение
Что именно решено сделать.

## Рассмотренные альтернативы
| Вариант | Плюсы | Минусы |
|---|---|---|
| ... | ... | ... |

## Последствия
Что изменится в результате принятого решения.
Компромиссы (trade-offs).
```

## 6. Требования к оформлению

### 6.1 Язык
- Технические документы пишутся на русском языке
- Технические термины (API, MR, CI/CD) не переводятся
- Имена собственные (GitLab, Qdrant, Neo4j) не переводятся

### 6.2 Структура
- Документ начинается с шапки: название, номер, версия, дата, утверждение
- Разделы нумеруются
- Таблицы предпочтительнее списков для структурированных данных

### 6.3 Актуальность
- Документация обновляется одновременно с кодом — в том же MR
- MR с изменением поведения сервиса без обновления документации не принимается на ревью
- Устаревшая документация помечается статусом `Устарело` и не удаляется
