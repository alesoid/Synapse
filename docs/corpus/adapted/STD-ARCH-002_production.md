## 1. Назначение

Настоящий регламент устанавливает правила доступа к продакшн-окружению Synapse Corp, порядок проведения изменений и действий в нештатных ситуациях. Продакшн-система содержит реальные пользовательские данные — любые действия выполняются осознанно и документируются.

---

## 2. Уровни окружений

| Окружение | Назначение | Доступ |
|---|---|---|
| `dev` | Локальная разработка | Все разработчики |
| `staging` | Тестирование перед релизом | Middle и выше |
| `production` | Боевая система | Senior, Tech Lead, DevOps |

Доступ к продакшн-окружению предоставляется по заявке, утверждённой Tech Lead. Матрица доступов — в документе `POL-SEC-001`.

---

## 3. Принципы работы с продакшном

- **Минимальный доступ.** Доступ к продакшну предоставляется только тем, кому он необходим для выполнения текущей задачи.
- **Никаких экспериментов.** Продакшн — не место для проверки гипотез. Эксперименты проводятся на staging.
- **Всё документируется.** Любое ручное вмешательство фиксируется в тикете Jira и сообщается в `#incidents`.
- **Парный доступ.** При критических операциях (миграции данных, аварийные правки) присутствие второго инженера обязательно.

---

## 4. Порядок деплоя в продакшн

### 4.1 Стандартный деплой

```
1. MR прошёл ревью и получил апрув (STD-ENG-001)
2. Изменения протестированы на staging
3. Release-ветка создана и протегирована (STD-ENG-002)
4. Деплой выполняется через CI/CD пайплайн — не вручную
5. После деплоя: проверить healthcheck всех сервисов
6. Мониторинг в течение 15 минут после деплоя
```

### 4.2 Hotfix

```
1. Инцидент зафиксирован в #incidents
2. Hotfix-ветка создана из main (STD-ENG-002)
3. Исправление минимально — только то, что нужно для устранения инцидента
4. Ревью минимум одним инженером (не автором)
5. Деплой через CI/CD с уведомлением команды
6. Postmortem в течение 24 часов после устранения
```

### 4.3 Запрещено

- Деплой в продакшн в пятницу после 17:00 и в выходные (кроме hotfix)
- Ручное редактирование файлов на продакшн-серверах
- Деплой без прохождения CI/CD пайплайна
- Деплой без уведомления команды

---

## 5. Доступ к базам данных продакшна

- Прямой доступ к продакшн-БД предоставляется только для диагностики и только через jump-хост
- Запросы `UPDATE`, `DELETE`, `DROP` на продакшн-БД выполняются только с явного согласования Tech Lead
- Все SQL-запросы к продакшн-БД логируются
- Дамп продакшн-данных для локальной отладки допускается только после анонимизации PII

---

## 6. Мониторинг и алертинг

После каждого деплоя инженер проверяет:

| Метрика | Целевое значение | Где смотреть |
|---|---|---|
| Healthcheck всех сервисов | Все `healthy` | `GET /health` каждого сервиса |
| Error rate | < 1% | Grafana → Error Rate dashboard |
| P95 latency | < 10 сек | Grafana → Latency dashboard |
| Количество активных трейсов | Без аномалий | Langfuse |

При отклонении от нормы — немедленно сообщить в `#incidents`.

---

## 7. Действия при инциденте

```
1. Зафиксировать в #incidents: что произошло, время, затронутые компоненты
2. Оценить severity:
   - P1 (критично): сервис полностью недоступен → немедленный rollback
   - P2 (высокий): деградация производительности → hotfix в течение 2 часов
   - P3 (средний): ошибки у части пользователей → исправление в текущем спринте

3. Откат (если необходимо):
   - CI/CD: запустить деплой предыдущего тега
   - Уведомить команду об откате

4. Postmortem: создать документ в Confluence в течение 24 часов
```

---

## 8. Rollback

- Возможность rollback обеспечивается сохранением предыдущего Docker-образа в registry
- Rollback выполняется через CI/CD пайплайн, не вручную
- После rollback — обязательный анализ причины и postmortem
