## 1. Назначение

Настоящая инструкция устанавливает обязательный порядок адаптации новых сотрудников и подрядчиков Synapse Corp. Цель — обеспечить безопасное и структурированное вхождение в работу: от подписания документов до первого продуктивного вклада в команду.

Инструкция распространяется на штатных сотрудников и удалённых подрядчиков. Раздел по документам различается для трудовых и контрактных отношений — ответственный за онбординг применяет соответствующий вариант.

---

## 2. Ответственные роли

| Роль | Зона ответственности |
|---|---|
| HR | Документы, льготы, координация процесса |
| IT-отдел | Выдача доступов, оборудование, настройка учётных записей |
| Нанимающий менеджер | План 30-60-90, первый тикет, еженедельные 1:1 |
| Tech Lead | Dev-окружение, архитектура, код-ревью процесс |
| Бадди | Неформальная поддержка, ответы на асинхронные вопросы |

---

## 3. Этап 1 — Пребординг (до первого рабочего дня)

Этап начинается в момент принятия оффера.

### 3.1 Пакет документов

Владелец: **HR**. Срок: не позднее 48 часов после принятия оффера.

- [ ] Трудовой договор или контракт подрядчика подписан обеими сторонами
- [ ] NDA подписано с верифицированной цепочкой аудита
- [ ] Соглашение о передаче прав на интеллектуальную собственность подписано
- [ ] Налоговые и кадровые документы оформлены в соответствии с законодательством РФ
- [ ] Проверка биографических данных или рекомендаций завершена
- [ ] Материалы для оформления льгот отправлены (для штатных сотрудников)

> **Важно.** Разработчик не должен делать коммиты в репозитории Synapse Corp до подписания соглашения о передаче прав на ИС.

### 3.2 Выдача IT-доступов

Владелец: **IT-отдел**. Срок: за 2–3 рабочих дня до даты выхода.

- [ ] Корпоративная почта и SSO-аккаунт созданы
- [ ] Отправлено приглашение в корпоративный менеджер паролей
- [ ] VPN настроен, MFA активирован
- [ ] Аккаунт GitLab создан с минимально необходимыми правами (только назначенные репозитории, без доступа к org-уровню)
- [ ] Доступ к облачной инфраструктуре настроен с корректной IAM-ролью — **без доступа к продакшн-окружению в первый день**
- [ ] Оборудование отправлено, факт доставки подтверждён
- [ ] Установлены инструменты коммуникации: Slack, Zoom
- [ ] Предоставлен доступ к Jira

### 3.3 Материалы для предварительного ознакомления

Владелец: **нанимающий менеджер**. Срок: за 3–5 дней до выхода.

- [ ] Обзорный документ по архитектуре или README проекта отправлен
- [ ] Доступ к инженерной вики предоставлен
- [ ] Документ с нормами работы команды отправлен (асинхронные часы, ожидания по PR, ритм встреч)
- [ ] План на 30-60-90 дней отправлен для ознакомления до первого дня
- [ ] Бадди назначен, отправлено письмо с представлением

---

## 4. Этап 2 — Первый день

Первый день — день построения доверия, не информационной перегрузки.

- [ ] Приветственный видеозвонок: менеджер + команда (не дольше 30 минут)
- [ ] Встреча 1:1 с менеджером: явный разбор плана 30-60-90
- [ ] IT-проверка: все аккаунты работают, VPN подключается, инструменты установлены
- [ ] Сессия настройки dev-окружения в паре с senior-инженером (Docker, локальный dev, IDE)
- [ ] Назначен первый тикет: небольшой, хорошо описанный, выполнимый за 1–2 дня
- [ ] Разбор процесса код-ревью: стратегия ветвления, соглашения по коммитам, шаблон PR
- [ ] Пройдено обязательное обучение по информационной безопасности

---

## 5. Этап 3 — Первая неделя

- [ ] Дни 1–2: погружение в инструменты коммуникации и процессы команды
- [ ] Дни 3–4: ориентация в основной кодовой базе
- [ ] Первое код-ревью: сотрудник проверяет существующий PR до того, как откроет свой
- [ ] Сессия парного программирования с senior-инженером (минимум 2 часа)
- [ ] Встреча 1:1 с tech lead: архитектурные решения, роадмап, приоритеты спринта
- [ ] Неформальный кофе-чат с 2–3 участниками команды (планируется явно)
- [ ] Чек-ин с менеджером в конце недели: что непонятно, что заблокировано, что идёт хорошо

---

## 6. Этап 4 — Первый месяц

- [ ] Первый PR влит в первые 5–7 рабочих дней
- [ ] 30-дневный ревью с менеджером: результаты по плану, корректировка доступов
- [ ] Аудит доступов: удалить временные и избыточные права, выданные при настройке
- [ ] Сотрудник документирует одну вещь, которую пришлось разбираться самостоятельно
- [ ] Запущен индивидуальный план развития: навыки на 2–3-й месяц, структура менторства

---

## 7. План на 30-60-90 дней

| Период | Фокус | Критерий успеха |
|---|---|---|
| Дни 1–30 | Изучить кодовую базу, выполнить 2–3 небольших тикета, пройти обучение по ИБ, освоить асинхронные нормы | Первый PR влит, аудит доступов чист |
| Дни 31–60 | Самостоятельно довести фичу средней сложности до конца, активно участвовать в код-ревью | Фича выкачена на staging |
| Дни 61–90 | Возглавить небольшой проект или спринт, предложить улучшение процесса | Измеримый вклад в скорость спринта |

## 9. Метрики успеха онбординга

| Метрика | Целевое значение |
|---|---|
| Время до первого коммита | ≤ 3 рабочих дня |
| Время до первого влитого PR | ≤ 7 рабочих дней |
| Удержание на 30-й день | 100% |
| Аккаунты без избыточных прав на 30-й день | 100% |
| Завершение обучения по ИБ | До конца 2-й недели |

---

## 10. Типичные ошибки — не допускать

- Создавать аккаунты в первый рабочий день — доступы должны быть готовы за 48 часов до выхода
- Выдавать избыточные права «для удобства» — использовать принцип минимально необходимых прав
- Допускать коммиты до подписания соглашения о передаче прав на ИС
- Ограничиваться ссылкой на документацию без живой сессии разбора
- Не фиксировать milestone первого PR в плане явно
- Не проводить аудит доступов на 30-й день
