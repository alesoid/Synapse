# ADR-008: Chunking Strategy — 500 токенов, overlap 50

**Статус:** Принято  
**Дата:** 11 мая 2026  
**Автор:** Алеся Мороз

---

## Scope

| Этап | Что реализовано | Статус |
|---|---|---|
| **MVP** | Фиксированный размер чанка 500 токенов, overlap 50 токенов, разбивка по заголовкам как приоритет | ✅ Текущее решение |
| **Scale** | Semantic chunking (разбивка по изменению семантики, а не по размеру); адаптивный размер чанка в зависимости от типа документа (`policy` → крупнее, `instruction` → мельче) | 🔜 Вне скоупа MVP |

---

## Контекст

Качество RAG критически зависит от стратегии разбивки документов на чанки. Слишком мелкие чанки теряют контекст; слишком крупные — размывают релевантность и увеличивают стоимость инференса. Дополнительное ограничение: каждый чанк становится узлом типа `Section` в Neo4j — его размер влияет на детализацию графа знаний.

Корпус MVP: IT-регламенты, технические стандарты, политики на русском языке. Типичный документ: 5–30 страниц, структурирован заголовками H1–H3.

---

## Решение

**Иерархический chunking:** приоритет разбивки по заголовкам Markdown (H1/H2/H3), с fallback на фиксированный размер 500 «токенов» и overlap 50 при отсутствии структуры.

```python
# backend/ingestion/chunker.py

# Шаг 1: разбивка по заголовкам (структурированные документы)
HEADING_PATTERN = re.compile(r"^(#{1,3})\s+(.+?)\s*$", re.MULTILINE)
# Кастомная реализация split_markdown_sections() — без зависимости от LangChain

# Шаг 2: fallback — фиксированный размер для неструктурированных блоков
TOKEN_PATTERN = re.compile(r"\S+")  # whitespace tokenizer (1 токен ≈ 1 слово)
# count_tokens() считает слова regex-ом; "500 токенов" ≈ 500 слов
```

**Примечание:** реализация использует кастомный regex-сплиттер и whitespace-tokenizer, а не LangChain `MarkdownHeaderTextSplitter` и tiktoken `cl100k_base`. Фактический размер чанка — 500 слов, не sub-word токенов. Это означает, что чанки содержат примерно 650–750 sub-word токенов в среднем по русским текстам.

**Параметры настраиваются** через env vars `CHUNK_SIZE=500` и `CHUNK_OVERLAP=50`.

## Альтернативы рассмотрены

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **Semantic chunking** | Разбивка по смысловым границам, а не по размеру — более точные чанки | Требует дополнительного embedding-прохода при индексации, увеличивает время ingestion | **Отклонён для MVP**, приоритет для Scale |
| **256 токенов** | Высокая точность retrieval на коротких фрагментах | Теряется контекст для длинных регламентов; увеличивается число чанков и стоимость хранения | **Отклонён** |
| **1024 токена** | Больше контекста в одном чанке | Снижается точность семантического поиска (вектор «размывается»); LLM получает избыточный контекст | **Отклонён** |
| **Sentence-level chunking** | Максимальная гранулярность | Слишком мелко для корпоративных регламентов — предложение без контекста раздела бессмысленно | **Отклонён** |
| **Фиксированный размер без overlap** | Проще реализация | Граница чанка разрывает предложения → потеря смысла на стыках | **Отклонён** |

---

## Trade-offs

**Плюсы 500 токенов / overlap 50:**
- 500 токенов — эмпирически подтверждённый «золотой стандарт» для RAG на документах среднего объёма (подтверждено исследованиями LlamaIndex, LangChain)
- Overlap 50 токенов (~10%) сохраняет контекст на границах чанков без значительного дублирования
- Иерархический подход: разбивка по заголовкам сохраняет логическую структуру документа — каждый чанк соответствует разделу, а не произвольному фрагменту
- Параметры настраиваемы через env — можно скорректировать без изменения кода

**Минусы:**
- Фиксированный размер не учитывает семантику — один чанк может содержать несвязанные мысли
- Overlap создаёт дублирование контента (~10% данных хранится дважды)
- Оптимальный размер зависит от корпуса и не был валидирован на golden dataset перед выбором

---

## Последствия

- Каждый чанк сохраняется в Qdrant с payload и становится узлом `Section` в Neo4j
- Среднее число чанков на документ: ~10–50 (при типичном документе 5–30 страниц)
- Смена размера чанка требует полной переиндексации (Qdrant + Neo4j)
- `backend/ingestion/chunker.py` логирует число извлечённых чанков на документ (FR-15)

---

## Compliance & Ethics

**Регуляторное соответствие:**
- Chunking выполняется локально — данные не покидают периметр
- Каждый чанк наследует `access_level` родительского документа — RBAC применяется на уровне каждого фрагмента

**Этические риски и меры снижения:**
- Риск разрыва чанком критически важного контекста (например, исключение из правила в следующем абзаце). Мера: overlap 50 токенов минимизирует потерю; иерархический splitter сохраняет логические границы разделов
- Риск того, что чанк содержит PII из документа. Мера: Input/Output Guardrails проверяют каждый чанк перед передачей в LLM (FR-25, FR-27)
