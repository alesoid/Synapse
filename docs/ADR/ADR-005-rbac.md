# ADR-005: RBAC — Chunk-level Access Control

**Статус:** Принято  
**Дата:** 11 мая 2026  
**Автор:** Алеся Мороз

---

## Scope

| Этап | Что реализовано | Статус |
|---|---|---|
| **MVP** | Числовой `access_level` (1–5), роль через HTTP заголовок `X-User-Role`, иерархический доступ (≤), фильтрация в Qdrant + Neo4j | ✅ Текущее решение |
| **Scale** | JWT-аутентификация + интеграция с LDAP/AD через Identity Provider, переход на ABAC для горизонтального разграничения (отдел А / отдел Б) | 🔜 Вне скоупа MVP |

> **Предупреждение:** передача роли через HTTP заголовок без JWT **не предназначена для production**. Решение приемлемо исключительно для демо в контролируемой среде. Перед вводом в эксплуатацию обязателен переход на JWT (см. Scale).

---

## Контекст

Synapse хранит корпоративные документы с разными уровнями конфиденциальности. Сотрудник с ролью Junior не должен получать ответы на основе документов уровня Manager — даже косвенно, через LLM генерацию. Требования:

- Фильтрация применяется до передачи данных в LLM (Security enforced before inference)
- Работает одновременно в Qdrant (векторный поиск) и Neo4j (graph traversal)
- Единый источник истины для уровней доступа
- Простота реализации и аудита
- MVP без JWT — роль передаётся через HTTP заголовок

---

## Решение

**Числовой `access_level` (int 1–5)** как единый механизм контроля доступа, применяемый на уровне каждого чанка и узла графа.

**Уровни:**
```python
ROLES = {
    "junior":  1,
    "middle":  2,
    "senior":  3,
    "manager": 4,
    "admin":   5
}
```

**Принцип:** пользователь видит документы где `doc.access_level <= user.access_level`.

**Реализация — три слоя:**

**Слой 1 — API Gateway:**
```python
async def get_current_user(role: str = Header(..., alias="X-User-Role")) -> int:
    if role not in ROLES:
        raise HTTPException(status_code=403)
    return ROLES[role]
```

**Слой 2 — Qdrant (retrieval-time):**
```python
query_filter = Filter(must=[
    FieldCondition(key="access_level", range=Range(lte=user_level))
])
```

**Слой 3 — Neo4j (traversal-time):**
```cypher
MATCH (n) WHERE n.access_level <= $user_level RETURN n
```

**Централизованный модуль:** `/backend/security/rbac.py`

## Альтернативы рассмотрены

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **JWT с claims** | Промышленный стандарт, не требует доверия заголовку, поддержка истечения токена | Избыточен для MVP — требует отдельного auth сервиса, усложняет разработку | **Отклонён для MVP**, запланирован для Scale |
| **Per-document ACL (список пользователей)** | Гибкое горизонтальное разграничение (пользователь А видит, пользователь Б нет) | Не масштабируется при большом корпусе, сложнее администрировать | **Отклонён** |
| **Постфильтрация (после LLM)** | Простота реализации — фильтруем уже готовый ответ | Небезопасно: LLM видит закрытый контент и может «запомнить» его в ответе, нарушает принцип Security enforced before inference | **Отклонён** (блокер по безопасности) |
| **Отдельная БД прав (Casbin, OPA)** | Мощный policy engine, поддержка сложных правил (ABAC, ReBAC) | Лишний сервис, избыточен для 5 ролей с линейной иерархией | **Отклонён** |
| **Row-level security в PostgreSQL** | Встроен в СУБД, не требует изменений в коде приложения | Только для SQL данных, не применимо к Qdrant и Neo4j | **Отклонён** |

## Trade-offs

**Плюсы числового access_level:**
- Простота: одно целое число на чанк/узел
- Единый источник истины — нет расхождения между Qdrant и Neo4j
- Retrieval-time фильтрация — LLM никогда не видит закрытый контент
- Легко аудировать: `audit_log` фиксирует каждый запрос с role и access_level
- Легко тестировать: 5 ролей × N документов = детерминированные тесты

**Минусы числового access_level:**
- Только иерархический доступ — нет горизонтального разграничения (отдел А не видит отдел Б при одинаковом уровне)
- Нет динамического изменения прав без переиндексации
- HTTP заголовок без JWT — не для production (достаточно для демо)

---

## Последствия

- `access_level` проставляется оператором при загрузке через `POST /ingest`
- Все чанки в Qdrant и все узлы в Neo4j имеют `access_level` — обязательное поле
- Попытка доступа к закрытому документу возвращает HTTP 403 с сообщением
- Audit log фиксирует все запросы: user_role, access_level, результат (AC-03)
- В Scale-этапе: JWT + LDAP/AD интеграция через Identity Provider, переход на ABAC при необходимости горизонтального разграничения

## Compliance & Ethics

**Регуляторное соответствие:**
- Chunk-level RBAC обеспечивает выполнение требований **ФЗ-152** в части разграничения доступа к персональным данным: пользователь не может получить информацию выше своего уровня доступа ни прямым запросом, ни косвенно через генерацию LLM
- Все попытки доступа фиксируются в audit log — выполнены требования к аудируемости системы обработки персональных данных
- Используется принцип Least Privilege: каждый пользователь получает минимально необходимый контекст для ответа на свой запрос

**Этические риски и меры снижения:**
- Риск подмены роли через заголовок `X-User-Role` в MVP (отсутствие JWT). Мера: явно задокументировано как ограничение MVP (не для production); в Scale-этапе заменяется на JWT + LDAP/AD. Для демо угроза приемлема в контролируемой среде
- Риск некорректного проставления `access_level` оператором при загрузке документа (человеческий фактор). Мера: валидация обязательности поля при ingestion, логирование всех операций загрузки с указанием оператора
- Риск что RBAC не применяется в одном из слоёв (Qdrant или Neo4j) из-за ошибки разработчика. Мера: интеграционные тесты проверяют оба слоя для каждой из 5 ролей (AC-03)
