# ADR-002: Vector Database — Qdrant

**Статус:** Принято  
**Дата:** 11 мая 2026  
**Автор:** Алеся Мороз

---

## Контекст

Synapse требует self-hosted векторную базу данных для хранения эмбеддингов корпоративных документов с возможностью фильтрации по метаданным (RBAC). Ключевые требования:

- Фильтрация по `access_level` в момент поиска (не постфильтрация)
- Хранение payload: `doc_id`, `text`, `access_level`, `last_updated`, `doc_type`
- Простое развёртывание в Docker
- Активная поддержка и документация
- Python client

---

## Решение

**Qdrant v1.9** — self-hosted, развёртывание через Docker образ `qdrant/qdrant:v1.9.0`.

**Схема коллекции:**
```python
client.create_collection(
    collection_name="chunks",
    vectors_config=VectorParams(size=768, distance=Distance.COSINE)
)
```

**RBAC фильтр при поиске:**
```python
client.search(
    collection_name="chunks",
    query_vector=embedding,
    query_filter=Filter(
        must=[FieldCondition(
            key="access_level",
            range=Range(lte=user_access_level)
        )]
    ),
    limit=10
)
```

## Альтернативы рассмотрены

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **Milvus** | Высокая производительность на больших объёмах, кластеризация, enterprise-кейсы | Значительно сложнее в оркестрации (требует etcd, pulsar), избыточен для MVP | **Отклонён** |
| **Weaviate** | Богатая экосистема модулей, GraphQL API, гибридный поиск из коробки | Тяжелее по ресурсам, более сложная конфигурация модулей, выше порог входа | **Отклонён** |
| **Chroma** | Максимально простой старт, удобен для прототипирования | Нет production-ready payload фильтров, позиционируется как dev/prototype инструмент | **Отклонён** |
| **pgvector** | Нет отдельного сервиса (расширение PostgreSQL), знакомый SQL-интерфейс | Хуже производительность на ANN поиске, нет специализированных индексов HNSW | **Отклонён** |
| **Pinecone / Weaviate Cloud** | Простое управление, автоматическое масштабирование | Облачные сервисы — данные покидают периметр, нарушают требование on-premise | **Отклонён** (блокер по безопасности) |

## Trade-offs

**Плюсы Qdrant:**
- Payload фильтрация применяется во время поиска — RBAC работает на уровне индекса
- Простой Docker запуск: одна команда, именованный volume
- Активное развитие (релизы каждые 2-3 недели)
- Хорошая документация, примеры на Python
- UI на порту 6333 для визуального контроля коллекций
- Поддержка named vectors и sparse vectors (для будущего hybrid BM25 + dense)

**Минусы Qdrant:**
- Community edition без кластеризации (достаточно для MVP)
- Меньше enterprise-кейсов чем у Milvus (компенсируется активным развитием)

---

## Последствия

- Коллекция `chunks` создаётся при инициализации системы
- RBAC фильтр применяется в `backend/retrieval/vector_retriever.py` (`build_qdrant_rbac_filter()`) при каждом поиске
- `access_level` и `last_updated` обязательные поля payload — проверяются при ingestion
- В Scale-этапе: Qdrant Cloud или Milvus при необходимости кластеризации

---

## Compliance & Ethics

**Регуляторное соответствие:**
- Qdrant развёртывается self-hosted в изолированном Docker-контуре — данные не покидают периметр, требования **ФЗ-152** соблюдены
- Qdrant распространяется под лицензией **Apache 2.0** — коммерческое использование допустимо без лицензионных ограничений
- Отсутствие телеметрии и коллбэков к внешним серверам подтверждено аудитом сетевого трафика (NFR-03)

**Этические риски и меры снижения:**
- Риск «утечки» закрытого контента через некорректно проставленный `access_level` при ingestion. Мера: валидация обязательности поля при загрузке документа (FR-14), audit log каждого поискового запроса
- Риск того что чанки одного документа получат разные уровни доступа из-за ошибки оператора. Мера: `access_level` наследуется от родительского документа автоматически в ingestion pipeline
